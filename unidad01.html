UNIDAD 0: Introducción a GitHub

Unidad Didáctica: "GitHub sin Miedo: De Cero a Colaborar en Equipo". Una guía progresiva, práctica y orientada a proyectos para dominar la plataforma esencial de control de versiones y trabajo colaborativo.

Sesión 1: ¿Qué es GitHub y por qué lo usa todo el mundo?

1. Contextualización y analogías sencillas 15 min

La analogía del Google Docs del Código

"Imaginad que estáis haciendo un trabajo en grupo en Word. Si os pasáis el archivo trabajo_v1.docx, trabajo_v2_final.docx, trabajo_este_si_que_si.docx, al final nadie sabe cuál es la versión buena. Google Docs resuelve esto guardando el historial y permitiendo editar a la vez. GitHub es como un Google Docs, pero diseñado para programadores."

Conceptos Clave Simplificados

Git vs. GitHub

Git es la herramienta/motor (el coche); GitHub es el garaje/plataforma web con red social donde aparcas el coche y lo enseñas a otros.

Repositorio (Repo)

La carpeta del proyecto en la nube que almacena el código, los archivos y todo el historial de cambios.

Commit

Una "foto" o punto de guardado de tu código en un momento concreto con un mensaje explicativo.

2. Ejemplo práctico en vivo 15 min

Demostración en directo conducida por el docente:

  • Crear una cuenta en GitHub (mostrar la interfaz limpia y el panel principal).
  • Crear un repositorio público llamado mi-primer-proyecto.
  • Crear un archivo README.md directamente desde la web y escribir una breve presentación usando Markdown básico (títulos, negritas, listas).
  • Guardar los cambios realizando el primer Commit changes.

3. Actividad práctica del alumnado 30 min

Reto 1

Crear su cuenta individual

Registrarse en GitHub con su correo de estudiante (si aún no disponen de una cuenta).

Reto 2

Crear repositorio público

Crear un repositorio público de prueba activando la opción de inicializar con README.md.

Reto 3

Personalizar README.md

Escribir su "Perfil de Desarrollador/a" (nombre, tecnologías que están aprendiendo, aficiones) usando formato Markdown.

Sesión 2: Ramas, Pull Requests y el "Camino Feliz" de Trabajo

1. Explicación del flujo de trabajo 15 min

La analogía del laboratorio/borrador

Las ramas permiten experimentar con total seguridad sin poner en riesgo la versión estable de la aplicación.

Rama principal (main)

Es la versión que funciona y está en producción (la app cliente que usan los usuarios). ¡No se toca directamente!

Ramas secundarias

Una copia aislada (ej. feature-branch) donde experimentas y desarrollas nuevas funcionalidades sin romper la app.

Pull Request (PR)

"Oye equipo, he terminado esta nueva función en mi rama. ¿Podéis revisarla antes de juntarla (merge) con la principal?"

2. Ejemplo paso a paso 20 min

Esquema Visual del Flujo de Trabajo

[Rama main] ----------------------------------------------> (App Funcional)
                 \                                 /
                  \-- [Rama: boton-login] -- (PR) /
  1. Crear una rama nueva: Crear la rama añadir-contacto directamente desde la interfaz web o mediante la terminal.
  2. Hacer cambios: Modificar o añadir una nueva línea en el archivo de texto o código dentro de la rama recién creada.
  3. Abrir un Pull Request: Mostrar cómo se especifica un título claro y una descripción detallada que justifique los cambios realizados.
  4. Hacer el Merge: Aprobar la revisión e integrar (fusionar) la rama secundaria dentro de la rama principal main.

3. Actividad práctica del alumnado 25 min

Reto en Solitario

  1. En el repositorio creado la sesión anterior, crear una rama llamada mejora-readme.
  2. Añadir enlaces a sus redes sociales o proyectos en esa rama.
  3. Abrir un Pull Request con destino a la rama main.
  4. Realizar el Merge y comprobar en la vista principal que la rama main se ha actualizado correctamente.

Sesión 3: Trabajo en Equipo y Resolución de Conflictos

1. La Dinámica Colaborativa 15 min

Fork vs. Clone / Collaborators

Colaboradores: Permitir a un compañero/a acceso directo de escritura para trabajar conjuntamente sobre el mismo repositorio sin necesidad de bifurcarlo.

Issues (Tareas/Bugs)

La lista centralizada de tareas pendientes, errores detectados y mejoras sugeridas dentro del panel del proyecto.

2. Proyecto práctico en parejas 45 min

Dinámica: "El juego del restaurante/menú"

Rol: Alumno A
  1. Crea un repositorio llamado menu-restaurante con un archivo menu.txt que contenga 2 platos básicos.
  2. Invita a Alumno B como colaborador/a en GitHub.
  3. Crea un Issue con el título: "Añadir sección de postres".
  4. Revisa el código enviado, deja un comentario de revisión y realiza el Merge.
Rol: Alumno B
  1. Acepta la invitación de colaboración recibida por correo o notificación.
  2. Se asigna el Issue creado por Alumno A.
  3. Crea una rama llamada seccion-postres y añade la carta de postres al archivo.
  4. Abre un Pull Request vinculando el Issue y etiquetando a Alumno A para su revisión.

Sesión 4 (Opcional / Avanzada): Publicación Web y Portafolio

1. GitHub Pages 20 min

Concepto: Servicio gratuito de alojamiento que permite publicar sitios web estáticos (HTML, CSS y JavaScript) directamente desde un repositorio de GitHub en cuestión de minutos.

Demostración: Subir un archivo index.html básico a la rama principal y activar GitHub Pages accediendo a la configuración del repositorio (Settings -> Pages).

Hosting Gratis

2. Proyecto Integrador Final 40 min

Entregable Esperado

Cada alumno/a debe subir un mini sitio web (o una landing page personal) a un repositorio de GitHub y activar **GitHub Pages** para obtener una URL pública e interactiva compartible.

Checklist de Evaluación

Estado Criterio de Evaluación Detalle de Validación
Nombre del Repositorio Uso de un nombre claro, descriptivo y sin espacios ni caracteres especiales.
Estructura del README.md Inclusión de título, descripción del proyecto, tecnologías usadas y enlace al despliegue.
Historial de Commits Existencia de al menos 2 commits con mensajes descriptivos y acordes a los cambios.
Flujo de Ramas y PR Uso documentado de al menos una rama secundaria y un Pull Request integrado.
Despliegue Funcional URL pública de GitHub Pages operativa mostrando el sitio web estático.
